Wake on LAN – project documentation

A complete guide to the code: architecture, the lifecycle of each part, a description of every function, and the reasoning behind the key design decisions.

1. Introduction

The project lets you remotely power on a computer on your home network (Wake-on-LAN) from a phone while you are outside that network. It consists of three programs:

client/ Mobile app

Expo / React Native, TypeScript. User account, list of computers ("targets"), list of ESP32 devices, a "Wake" button.

server/ Relay server

Python 3.11+, asyncio, PostgreSQL (asyncpg). Accounts, sessions, device pairing, forwarding commands to the ESP32.

esp_client/ ESP32 firmware

ESP-IDF, C++. Persistent connection to the server, receives WAKE_UP, sends a UDP magic packet on the local network.

The core idea: the ESP32 connects to the server by itself (an outbound connection), so no ports need to be opened on the home router. Only the server is publicly reachable. The app and the ESP32 never talk to each other directly.

Code conventions

  • Command names are identical in all three programs: Cmd in Python (protocol.py), the Cmd object in TS (protocol.ts), CMD_* constants in C++ (protocol.hpp). To follow a command, search the whole repository for its name, e.g. WAKE_UP.
  • A command handler on the server is a function decorated with @router.route(Cmd.X, schema=..., auth=..., rate_limit=...). The decorator states all entry conditions: argument types, required login state and rate limit.
  • A domain error is always raise CommandError(Err.CODE); the dispatcher turns it into NACK ["code"]. In the app the same code arrives as WolError.code.
  • Repositories (*Repo) return None when a lookup finds nothing, and raise NOT_FOUND when a mutation hits no row (including someone else's row).
  • Comments in the code describe constraints that the code itself cannot show (e.g. races). Read them carefully – there is usually a decision from chapter 11 behind them.

3. Architecture

Big picture

All three programs use the same frame format: one JSON object per line, {"COMMAND":[arg1,arg2]}\n. Messages to the server are at most 4096 bytes; server replies to the client may be longer (the app accepts up to 64 KiB). Details in chapter 9.

5. Lifecycle – what runs, in order

5.1 Server start and stop server

  1. python -m wol_server runs __main__.main().
  2. load_dotenv(server/.env) – loads variables from the file into os.environ.
  3. Settings.from_env(os.environ, base_dir) – validates every variable (ports, pepper ≥ 32 chars, DATABASE_URL, certificate files exist, SMTP). Any error ends the process with configuration error: ... before anything starts.
  4. logging.basicConfig(level=...).
  5. asyncio.run(run(settings)) – from here on everything runs in a single event loop.
  6. Database(...).connect() – creates the asyncpg pool (min 1, max DB_POOL_SIZE, 10 s query timeout).
  7. db.migrate() → schema.migrate(conn) – inside a transaction holding an advisory lock (pg_advisory_xact_lock), applies missing migrations and records them in schema_migrations. A database newer than the code raises SchemaError.
  8. Mailer(settings.smtp) or None (then a warning: password reset disabled).
  9. Services.create(db, Security(pepper), mailer=...) – creates repositories, Registry, RateLimiter. Security.__init__ immediately computes a "dummy" Argon2 hash (used when logging into a non-existent account).
  10. build_dispatcher() – collects routers from all handlers/* modules into one Dispatcher (and checks there are no duplicate commands).
  11. WolServer.start():
    • build_ssl_context() – TLS ≥ 1.2, no compression, loads certificate and key;
    • for each role (CLIENT, DEVICE) asyncio.start_server(partial(_on_connect, role), host, port, limit=4096) – without ssl=, TLS is started manually later;
    • starts the _purge_loop() task.
  12. serve_forever() – waits on both servers. Every new TCP connection becomes a new _on_connect coroutine (see 5.2).
  13. Every hour _purge_loop deletes expired sessions, claims and reset codes.
  14. Shutdown (Ctrl+C / SIGINT): KeyboardInterrupt interrupts serve_forever, the finally block calls WolServer.close() (cancels purge, stops listening, closes all connections and waits for them), then mailer.close() (waits up to 20 s for queued mail), and finally db.close().

5.2 Lifecycle of one connection on the server server

  1. _on_connect(role, reader, writer) – reads the client IP.
  2. ConnectionLimiter.acquire(ip) for the general limit (20/IP, 1000/port). Exceeded → _abort(writer), done.
  3. acquire(ip) for the "unauthenticated" limit (5/IP, 256/port). Exceeded → release the first limit and _abort.
  4. writer.start_tls(ssl_context, ssl_handshake_timeout=5) – only now the TLS handshake. Failure → _abort.
  5. _run_connection: adds the Connection to the active set, creates Context(services, Session(role, ip), conn).
  6. _serve(ctx, on_authenticated) – loop:
    • computes the timeout via _read_timeout: before login = time left until the 30 s deadline counted from connect; authenticated ESP = 30 s; authenticated client = 300 s;
    • conn.read_message(timeout):
      • TimeoutError → _on_idle: for an authenticated ESP sends PING and continues unless silence has lasted ≥ 90 s; otherwise the connection ends;
      • ProtocolError (bad JSON) → NACK bad_frame; before login the third bad frame ends the connection;
      • FrameTooLong → NACK frame_too_long and end;
      • None (peer closed) → end;
    • Dispatcher.dispatch(ctx, message) → reply (see 5.3);
    • if the session is now authenticated → on_authenticated() releases the "unauthenticated" slot (once);
    • if there is a reply → conn.send(reply) (10 s write deadline);
    • the loop also ends when a handler sets session.close_requested (e.g. LOGOUT) or the connection was closed from outside (e.g. kick_user).
  7. _cleanup(ctx): for an ESP – registry.detach_device + devices.touch (writes last_seen_at); for a client – registry.remove_client. Then the socket is closed.
  8. The finally block in _on_connect releases both connection limits.

5.3 Handling one command (Dispatcher.dispatch) server

  1. Looks up the route by (session.role, message.command). Missing → NACK unknown_command. This way an ESP cannot send a client command and vice versa.
  2. Checks route.auth: True requires login (unauthenticated), False requires no login (already_authenticated), None – either.
  3. _matches(schema, args) – count and exact types of arguments (type(arg) is kind, so true does not pass as int). Mismatch → bad_args.
  4. If the route has a rate_limit → limiter.allow(name, ip). No token → rate_limited.
  5. For commands requiring login – _session_still_valid: at most once every 60 s checks the database that the session token still exists. If not → close_requested = True and invalid_token.
  6. Calls the handler: await route.handler(ctx, *message.args).
  7. CommandError(code) → NACK [code]; any other exception → log entry and NACK internal. A handler may return None – then nothing is sent (e.g. WAKE_ACK from the ESP).

5.4 App start app

  1. Expo Router renders app/_layout.tsx → RootLayout → <SessionProvider> → <RootNavigator>.
  2. SessionProvider starts with status "loading"; RootNavigator shows only a spinner.
  3. Effect 1: api.onSessionInvalid = () => signOutLocally() – from now on any token rejection by the server signs the user out locally.
  4. Effect 2 (one-shot): reads the token, user name, host and port from SecureStore in parallel. If the read throws (e.g. the Keystore key can no longer decrypt the data), it clears the stored session, configures api with the default address and no token, and sets status = "signedOut" instead of staying on the spinner.
  5. Builds the server address (saved, or the default from app.json → expo.extra) and calls api.configure(address, token). No connection is opened yet.
  6. flushPendingLogout() in the background – if a previous logout never reached the server, tries to revoke the old token now.
  7. No token → status = "signedOut" → the (auth) group is shown (login screen).
  8. Token present → immediately status = "signedIn" (optimistically, with the stored name), tabs are shown. In the background api.connect() → RESUME; on success the user name is refreshed. If the server rejects the token, onSessionInvalid switches to the login screen.
  9. RootNavigator uses Stack.Protected guard={signedIn}: a status change automatically switches the available routes.

5.5 A typical app request (e.g. list of computers) app

  1. The (tabs)/index.tsx screen gains focus → useRemote(loadPanel) → useFocusEffect → reload().
  2. reload bumps the generation counter, sets loading and calls loadPanel() = Promise.all([api.listTargets(), api.listDevices()]).
  3. api.listTargets() → private call(LIST_TARGETS) → ensureSession().
  4. ensureSession: if there is no active session promise, creates one with openSession() and memoizes it. The second parallel call (listDevices) gets the same promise – only one RESUME.
  5. openSession → open() → WolConnection.connect(host, port): TcpSocket.connectTLS with ca: serverCertificate (pinned certificate), 10 s timeout, on connect starts a PING interval every 60 s.
  6. conn.request(RESUME, [token]) → writes the line to the socket and appends {resolve, reject, timer} to the pending queue.
  7. Data arrives → onData fills the buffer and splits on \n → onLine → decode → takes the first queue entry → ACK/PONG = resolve, NACK = reject with WolError(code).
  8. After a successful RESUME the actual request(LIST_TARGETS) runs; the reply passes the type guard list(value, isTarget) – a wrong shape gives protocol_error.
  9. The result returns to useRemote; if a newer reload started meanwhile (another generation), it is ignored. Otherwise setData and the list renders.
  10. Error → describeError → message in ErrorText. When the code is invalid_token, WolApi.sessionRevoked() clears the token and calls onSessionInvalid (sign-out).

5.6 App in background and back app

  • AppState = "background" (and status signedIn) → api.disconnect(): the connection is closed, the session promise cleared.
  • AppState = "active" → flushPendingLogout() and api.connect() (new connection + RESUME).
  • If the connection breaks by itself (error, request timeout), WolConnection.fail calls onClosed → WolApi clears session; the next call() reconnects automatically.

5.7 ESP32 boot and main loop firmware

  1. app_main() (called by ESP-IDF after the bootloader).
  2. init_nvs() – nvs_flash_init(); with NVS encryption it reads (or on first boot generates) the keys in the nvs_keys partition. A broken partition is erased and initialised again.
  3. wifi::start(SSID, password) – station mode; the event handler reconnects after every disconnect and sets/clears CONNECTED_BIT.
  4. xTaskCreate(client_task, "wol_client", 10 KB, prio 5) – a separate FreeRTOS task running WolClient.
  5. start_console() – UART REPL with the claim <token> command. app_main returns; the tasks keep running.
  6. WolClient::run() – infinite loop:
    • load_identity() – credentials from RAM or NVS (credentials::load); if they only exist in RAM, retries saving them;
    • no identity → pending_claim_token(): token from the console (NVS claim) or from Kconfig, provided it is not marked as used;
    • neither → logs "device is not paired" and ulTaskNotifyTake – the task sleeps until the claim command wakes it (xTaskNotifyGive);
    • wifi::wait_connected() – waits for an IP address;
    • TlsConnection::connect(host, port, ca_pem, skip_cn) – TLS with pinned certificate; failure → backoff();
    • auth_with_credentials() (DEVICE_AUTH) or claim_device() (DEVICE_CLAIM); failure → close and backoff();
    • success → reset backoff to 2 s and session_loop();
    • after session_loop returns – close the connection and loop again.
  7. session_loop(): read_line in 5 s ticks. Timeout → if nothing arrived for 60 s, sends PING; if the PING is not answered within 15 s – session ends. Line → Packet::decode → handle():
    • PING → PONG; PONG/ACK → nothing;
    • WAKE_UP → handle_wake_up (magic packet, then WAKE_ACK);
    • SET_SECRET → handle_set_secret (write to NVS, then SECRET_ACK);
    • UNPAIRED → forget_identity() and exit (the ESP waits for a new claim);
    • NACK and unknown commands → log only, never a reply.

6.4 Device secret rotation

  1. App: DevicesScreen.rotate → confirmation → api.rotateDeviceSecret(id) (20 s timeout).
  2. Server devices.rotate_device_secret: the device must be online and belong to the user (otherwise device_offline / not_found).
  3. Under link.rotation_lock (rotations of one device run one at a time): new 32 B secret → devices.stage_secret stores its HMAC in next_secret_hash. The old secret still works.
  4. link.request(SET_SECRET, secret, timeout=5) → ESP handle_set_secret: first writes to NVS (save_secret), only then SECRET_ACK.
  5. Server: devices.promote_secret – next_secret_hash becomes secret_hash. If the ESP rebooted meanwhile and logged in with the new secret, authenticate() already promoted it – promote_secret still reports success.
  6. No acknowledgement → the server disconnects the ESP (registry.detach_device) and returns device_unreachable. It is unknown whether the ESP stored the new secret, so its next DEVICE_AUTH settles it: logging in with the new secret promotes it, logging in with the old one clears next_secret_hash. Another rotation needs the device online, so it always starts from a clean state and cannot overwrite the secret the ESP actually holds.

6.5 Password reset by e-mail

  1. App: LoginScreen.openReset saves the server address → ResetPasswordScreen, "email" step → session.requestPasswordReset → api.requestPasswordReset on a separate, short-lived connection (withSideConnection).
  2. Server password_reset.request_password_reset: no SMTP → reset_unavailable. E-mail validation. The per-e-mail limit is silent (always ACK []). Unknown address → also ACK [].
  3. Known address: new_reset_code() (10 chars, Crockford alphabet) → resets.create (replaces the previous one, resets attempts, 15 min TTL) → mailer.send_later (sent in the background, the reply does not wait) → ACK [].
  4. The app moves to the "code" step. normalizeResetCode accepts spaces, dashes, lowercase and O/I/L.
  5. api.resetPassword → authenticate(RESET_PASSWORD, ...) (new connection). Server: validation, limit per (e-mail, IP), resets.consume (constant-time comparison; a wrong guess increments the counter, the 50th wrong one deletes the code).
  6. Success: users.change_password (new hash + _revoke_credentials: epoch +1, delete sessions, codes and claims) → registry.kick_user (disconnects all apps) → start_session with the new epoch → ACK [token, name]. The app stores the token and is signed in.

6.7 Removing a device and deleting an account

  • REMOVE_DEVICE: devices.delete (targets assigned to the device get device_id = NULL through ON DELETE SET NULL) → registry.unpair_device sends UNPAIRED and closes the connection → ESP forget_identity() erases credentials from NVS and waits for a new claim.
  • DELETE_ACCOUNT: confirm_password → list of device IDs → users.delete (cascade removes sessions, claims, devices, targets, codes) → unpair_device for each → kick_user → end_connection. App: signOutLocally.

9. Protocol summary

Full specification: server/PROTOCOL.md (Polish).

  • Frame: {"COMMAND":[arguments]}\n, max 4096 B to the server (server replies to the app up to 64 KiB). Reply: {"ACK":[...]} or {"NACK":["code"]}.
  • Client port: the client sends a request, waits for the reply, and only then sends the next. Replies carry no ID.
  • Device port: the server sends the ESP WAKE_UP [request_id, mac] and SET_SECRET [request_id, secret]; the ESP acknowledges with WAKE_ACK/SECRET_ACK [request_id]. PING/PONG both ways. UNPAIRED – the device was removed.
  • The ESP never replies to ACK/NACK, and the server does not reply to PONG, WAKE_ACK, SECRET_ACK – loops are impossible.

11. Architectural decisions and their rationale

Each decision: what was chosen, why, and the cost (trade-off).

11.1 System and network

D1. A relay server instead of direct access to the home network

Why: a magic packet only works inside the local network (L2 broadcast). To wake a computer from outside, something at home has to send it. Direct access from the internet would require port forwarding, a static IP or DDNS, and would expose a home device to attacks.

Cost: a publicly reachable server and database are needed; the server is a single point of failure.

D2. The ESP32 opens an outbound connection and keeps it open

Why: outbound connections pass through NAT and firewalls without router configuration. A persistent connection lets the server push WAKE_UP immediately, without polling.

Cost: heartbeats on both sides (D56), reconnect with backoff (D55), handling of "hanging" connections after an ESP reboot (D34).

D3. Separate ports for the app (8443) and devices (8444)

Why: the connection's role follows from the port, not from what the peer claims – an ESP physically cannot call an app command and vice versa (routing by (role, command)). Connection limits are counted separately, so flooding one port does not lock out the other. Different timeouts (300 s vs 30/90 s heartbeat). The firewall can treat the two ports differently.

Cost: two ports to open on the server.

D4. Wi-Fi and server address compiled into the firmware (no BLE/SoftAP)

Why: provisioning over BLE or an access point is a lot of code, extra attack surface and a separate screen in the app. For a device installed once by an owner with USB access, Kconfig is enough.

Cost: changing the Wi-Fi network or server address requires rebuilding and reflashing the firmware.

11.2 Protocol

D5. A custom protocol: JSON lines over raw TLS instead of HTTP/WebSocket

Why: a bidirectional, persistent channel is needed (the server initiates WAKE_UP). On the ESP32, esp_tls + cJSON is enough, no HTTP/WS client. The {"CMD":[args]}\n frame is trivial to parse in all three languages and readable in logs. The server needs no web framework.

Cost: no off-the-shelf tooling (curl, browser, HTTP proxies); custom framing, timeouts and heartbeat. The app needs the native react-native-tcp-socket module (D39).

D6. 4096 B frame limit and nesting limit

Why: bounds the memory used by one connection (especially on the ESP). The server sets the StreamReader limit, the ESP checks nesting ≤ 4 before cJSON (recursion could overflow the 10 KB task stack), and Python catches RecursionError. The limit applies to messages sent to the server and to the ESP; list replies to the app are longer, so the app accepts lines up to 64 KiB.

Cost: lists must fit in 64 KiB – hence the 10-device and 64-target limits (the worst-case LIST_TARGETS is about 55 KB).

D7. Strict argument types

Why: type(arg) is kind rejects "1" for 1 and true for a number (in Python bool is a subclass of int). The schema in the route decorator means the handler already receives correct types.

Cost: clients must follow the types exactly.

D8. App: one request at a time, replies without IDs

Why: simpler protocol and server – a reply always belongs to the last request. The app performs few operations anyway; WolConnection can still queue multiple promises because the server replies in order.

Cost: a timeout on one request must close the whole connection (a late reply would land on the next request). A long WAKE_UP blocks further commands on that connection.

D9. Server → ESP channel with request_id and acknowledgements

Why: one ESP can receive concurrent requests from several of the user's apps. The ID matches an acknowledgement to the right Future, and late acknowledgements are safely ignored.

Cost: in-memory pending state; cleanup on disconnect (DeviceLink.close).

D10. End-to-end wake confirmation

Why: the user sees "Sent" only once the ESP actually sent the magic packet. A plain "server accepted it" would mislead when the ESP is dead but its TCP connection is still open.

Cost: extra waiting (up to 5 s) and a WAKE_ACK command. It does not guarantee the computer woke up (UDP, no confirmation from the PC).

D11. No replies to replies

Why: the ESP does not reply to ACK/NACK/unknown commands, and the server does not reply to PONG/*_ACK. This rules out endless "NACK to a NACK" loops when one side misbehaves.

Cost: errors are visible only in logs.

11.3 Security

D12. TLS with a pinned (self-signed) certificate in the app and firmware

Why: no domain or public CA is needed; the server can run on a bare IP. Pinning protects against MITM even with a compromised system CA. On the ESP the certificate bundle is disabled (CONFIG_MBEDTLS_CERTIFICATE_BUNDLE=n) – it trusts exactly one certificate. TLS 1.2 minimum, no compression.

Cost: replacing the certificate (e.g. when it expires after 365 days) requires a new app build and new firmware.

D13. TLS started after the connection limits are checked

Why: a TLS handshake costs CPU. start_server without ssl and a manual start_tls in _on_connect means excess connections are rejected before the expensive handshake. Connections mid-handshake count towards the "unauthenticated" limit.

Cost: slightly more complex code than start_server(ssl=...).

D14. Protection against floods of unauthenticated connections

Why: a 30 s deadline counted from connect (not from the last message), max 3 bad frames, and a separate 5/IP limit for unauthenticated connections – an attacker cannot hold many cheap connections and starve real clients.

Cost: a slow client must log in within 30 s.

D15. Passwords: Argon2, in a thread, with a semaphore and a dummy hash

Why: Argon2 is the current GPU-resistant standard. Running it in to_thread keeps the event loop free, and the semaphore (4) caps CPU/RAM under a login flood. The dummy hash equalises response time for non-existent accounts. needs_rehash lets parameters be tightened without a migration.

Cost: a login takes tens to hundreds of ms; throughput is bounded by the semaphore.

D16. Tokens stored as HMAC-SHA256 with a pepper

Why: tokens (session, claim, device secrets, reset codes) are random and long, so they do not need slow hashing like passwords. HMAC is deterministic – it can serve as a primary key and be looked up without a scan. A leaked database without the pepper (which lives only in .env) is useless.

Cost: changing TOKEN_PEPPER invalidates all sessions and all paired devices.

D17. A session token instead of the password on the phone

Why: the password is not stored in the app; the token can be revoked independently (LOGOUT, LOGOUT_ALL). Stored in expo-secure-store (Keystore). Sliding 30-day validity – an active user never has to log in again. Max 20 sessions per account limits "leakage" from old devices.

Cost: a stolen token grants access until it is revoked.

D18. Session epoch (session_epoch) against login-vs-revocation races

Why: while a LOGIN is in progress (password checking takes time), someone may run CHANGE_PASSWORD/LOGOUT_ALL; the login could then create a session after the revocation. The epoch read before password verification is compared when storing the session, with SELECT ... FOR SHARE (waits for an ongoing revocation to commit). Additionally bind_session checks the session exists after registering the connection.

Cost: an extra column, transaction and query at login.

D19. Revocation: immediate disconnect + periodic re-check

Why: kick_user immediately closes connections in this process. Re-checking the session in the database every ≤ 60 s (instead of on every command) guarantees correctness in edge cases without loading the database.

Cost: up to 60 s delay in the worst case (e.g. with multiple server instances, where kick_user only acts locally).

D20. Login limits count only failures, per (account, IP) and per account

Why: counting all attempts per account would let a stranger lock the owner out. Counting failures per (account, IP) (10/min) stops guessing from one address; a loose per-account limit (100/h) stops distributed guessing. Successful logins do not consume the limit.

Cost: a botnet with many IPs gets up to 100 attempts/h per account – enough protection for a reasonable password.

D21. In-memory limits (token bucket)

Why: no extra infrastructure (Redis), constant-time operations, easy tests with an injected clock. Pruning at 50,000 buckets bounds memory.

Cost: limits reset on restart and are not shared between instances.

D22. Password reset does not reveal whether an e-mail exists

Why: REQUEST_PASSWORD_RESET always returns ACK [], the per-e-mail limit acts silently, the mail goes out in the background (response time does not depend on SMTP). The code has ~50 bits, 15 min, single use, an alphabet without confusable characters. The 50-attempt total is deliberately high – a stranger cannot "burn" the owner's code, and guessing is infeasible anyway with 5/min per (e-mail, IP).

Cost: a user with a typo in the address gets no feedback.

D23. REGISTER deliberately reveals taken names (account_exists)

Why: the username has to be unique and visible at registration anyway, so hiding it would be pretend security and hurt UX. The risk is bounded by per-IP and per-e-mail limits (3/10 min).

Cost: slowly probing whether an address is registered is possible.

D24. Password confirmation for sensitive operations

Why: CHANGE_PASSWORD, CHANGE_NAME, DELETE_ACCOUNT require the password (confirm_password, 5/min). A token alone (e.g. from an unlocked phone) is not enough to take over or delete the account.

Cost: the user has to remember the password.

D25. "Not found" instead of "not yours"

Why: every device/target query is scoped to user_id; someone else's object yields not_found, same as a non-existent one. Other users' IDs cannot be probed. An out-of-range record_id also yields not_found.

Cost: none.

D26. Input validation: normalisation and rejecting control characters

Why: names are normalised to NFC (the same name written differently does not create duplicates), Unicode category "C" characters are rejected (prevents RTL tricks, invisible characters, log injection). A MAC with the multicast bit would be useless.

Cost: rules have to be maintained in two places (server and validation.ts).

D27. Flash and NVS encryption on the ESP32; release profile with Secure Boot v2

Why: the device_secret is enough to impersonate the device. Without encryption it can be read from flash over UART. Development mode still allows reflashing; Release + Secure Boot v2 blocks readout and unauthorised firmware.

Cost: the first boot permanently writes a key into eFuse; Release and Secure Boot are irreversible; a partition table change requires erase-flash and re-pairing. The bootloader is larger – partition offset 0x10000.

11.4 Server

D28. Single-threaded asyncio

Why: the server is mostly I/O (many long-lived connections, little computation). One event loop = no locks in Registry and RateLimiter (see the comment in registry.py). CPU work (Argon2) and blocking I/O (SMTP) go to threads.

Cost: one core for the logic; in-memory state ties it to a single instance.

D29. A decorator-based router and the dispatcher as the single control point

Why: entry conditions (role, login, types, limit) are declared next to the handler and enforced in one place. The handler contains only domain logic. Duplicates are detected at startup. A new command = a new decorated function.

Cost: a bit of "magic" – you need to know the decorator registers the route when the module is imported.

D30. Domain errors as the CommandError exception

Why: any layer (validation, limiter, repository) can abort a command with a single raise, without passing codes upward. Unexpected exceptions become internal with a log entry – details never leak to the client.

Cost: control flow via exceptions.

D31. Dependency injection through Services/Context

Why: no globals; tests substitute a FakeMailer, a fast hasher, their own RateLimiter with a clock, shorter Timeouts and lower ConnectionLimits.

Cost: more wiring in constructors.

D32. PostgreSQL with asyncpg, hand-written SQL, invariants in transactions

Why: an async driver fits asyncio. Hand-written SQL gives full control over locking: FOR UPDATE on the user when checking limits, FOR SHARE for the epoch, DELETE ... RETURNING for single-use claims. Unique indexes on lower() provide case-insensitivity.

Cost: no ORM – row mapping is manual (_user, _device, _target).

D33. Migrations in code, forward-only, with an advisory lock

Why: the server prepares the database itself at startup – no separate tool. The lock protects against two instances migrating at once. Older code will not start on a newer database.

Cost: no rollback of migrations.

D34. A new device connection replaces the old one

Why: after an ESP reboot, the old TCP connection may "hang" on the server until the heartbeat timeout. Replacing it immediately routes requests to the new connection; detach_device checks connection identity, so cleaning up the old one does not unregister the new one.

Cost: two devices with the same secret would keep kicking each other (a warning log reveals it).

D35. Two-phase secret rotation

Why: if the SECRET_ACK gets lost or the ESP reboots mid-rotation, neither side may end up with a secret the other does not know. The server accepts both old and new until the new one is confirmed or used. Without a confirmation the server disconnects the ESP, and the secret used on the next login becomes the only valid one, so a later rotation cannot overwrite the secret the ESP actually holds. rotation_lock prevents two rotations from interleaving. The ESP writes to NVS before acknowledging.

Cost: an extra column and logic in authenticate/promote_secret.

D36. Targets survive device removal

Why: ON DELETE SET NULL – after replacing an ESP the user does not lose the list of computers, they just reassign them to the new device (ASSIGN_TARGET).

Cost: a "target without device" state (no_device) the UI must handle.

D37. Configuration validated at startup (fail fast)

Why: errors like "certificate missing", "pepper too short", "SMTP password without TLS" appear immediately with the variable name, rather than at runtime.

Cost: none.

D38. E-mail sent in the background

Why: the reply does not wait for SMTP (fast and constant-time, see D22); SMTP errors never reach the client. Mailer.close gives tasks time on shutdown.

Cost: no durable queue – a mail in flight is lost if the process crashes (the user just requests a new code).

11.5 App

D39. Expo / React Native with react-native-tcp-socket

Why: one TypeScript codebase, fast development, EAS Build for APKs. A raw TLS socket is required by D5; this module also supports a custom CA (ca) for certificate pinning.

Cost: does not run in Expo Go – needs expo-dev-client or a built APK. The certificate is an asset (metro.config.js adds the pem extension).

D40. One persistent session in the WolApi singleton

Why: one connection per app, authentication (RESUME) once per connection rather than per request. Memoising the session promise means parallel calls (e.g. Promise.all on the main screen) wait on the same RESUME. Automatic reconnect on the next call.

Cost: global state; screens share one request queue (D8).

D41. Side connections for password reset and token revocation

Why: REQUEST_PASSWORD_RESET requires the "unauthenticated" state, and revokeToken logs in with a different token. A separate short-lived connection leaves the main session untouched.

Cost: an extra TLS handshake.

D42. A single close path and socket identity checks in WolConnection

Why: every way of closing goes through shutdown(), which settles every promise and timer; event handlers check this.socket === socket. Nothing from an old socket can affect a new one, and no promises are left hanging.

Cost: a bit more guard code.

D43. Runtime validation of server replies

Why: TypeScript does not check network data. The isDevice/isTarget guards ensure a screen never gets a malformed object (e.g. with a mismatched server version) – instead of a render crash there is a clear protocol_error.

Cost: guards must be updated with the protocol.

D44. Form validation mirroring the server

Why: errors appear instantly, without a round trip and without consuming rate limits. The server remains the source of truth. Lengths are counted in code points to agree with Python (emoji).

Cost: two copies of the rules (a comment in validation.ts points to the source).

D45. Optimistic "signed in" at startup

Why: with a stored token the app shows the panel immediately – no waiting for the network. An offline server shows up as an error on the screen, and an invalid token signs out via onSessionInvalid.

Cost: the panel may briefly be visible for an already revoked session.

D46. Deferred logout (pending_logout)

Why: logout always works locally, even offline. A token that could not be revoked is stored and revoked at the next opportunity (startup, returning to the app, sign-in) – no orphaned valid session remains.

Cost: an extra SecureStore entry and retry logic.

D47. Disconnect in the background

Why: Android kills background sockets anyway; disconnecting explicitly saves battery and makes state predictable. On return – a new connection and RESUME.

Cost: a handshake every time the app comes back.

D48. Expo Router with Stack.Protected

Why: route availability follows directly from session status – no manual navigation reset after logout, and a signed-in user cannot reach the login screen. File-based routing mirrors the screen structure.

Cost: depends on a recent Expo Router version.

D49. useRemote: load on focus with a generation counter

Why: after returning from an edit screen the list is fresh without manual refresh and without a global state store. The generation counter drops results of older requests.

Cost: more requests than with a cache.

D50. PromptModal instead of Alert.prompt

Why: Alert.prompt exists only on iOS. A custom modal supports multiple fields, password fields and server errors.

Cost: a custom component to maintain.

11.6 Firmware

D51. Pairing with a one-time claim token

Why: the user never types a password into the device. A 128-bit token, 10 min, one active per account, bound to the account. The server issues the ESP its own identity (device_id + 256-bit secret), independent of the password. Two paths: UART console (no reflash) or Kconfig.

Cost: requires USB/UART access or a firmware rebuild.

D52. The ESP remembers the last used token

Why: a Kconfig token is compiled in forever. Without this record, after UNPAIRED or data loss the ESP would send it on every boot, consuming rate limits and cluttering logs. With no fresh token it does not connect at all – it waits for claim.

Cost: an extra NVS key.

D53. Credentials also kept in RAM

Why: if writing to NVS fails (e.g. no space), the device stays paired until reboot and keeps retrying the write. Without this, a failed write after DEVICE_CLAIM would mean a consumed token and no identity.

Cost: the creds_persisted_ flag and extra branches.

D54. C++ without exceptions, results via bool/optional/esp_err_t

Why: exceptions in ESP-IDF increase binary size and are disabled (CONFIG_COMPILER_CXX_EXCEPTIONS=n). Explicit return values match the ESP-IDF API. RAII (NvsHandle, the TlsConnection destructor) manages resources.

Cost: every call must be checked by hand.

D55. Exponential backoff with jitter

Why: when the server is down the ESP does not hammer it, and jitter spreads reconnects of many devices after a server restart. After a successful session the backoff resets to 2 s.

Cost: up to ~90 s of unavailability after the server comes back.

D56. Heartbeats on both sides, different thresholds

Why: the server pings after 30 s of silence, so normally the ESP does not need to – its 60 s threshold only fires when the server stopped sending (half-open connection). Both sides detect a dead connection in bounded time.

Cost: a little traffic every 30 s.

D57. Reads with select plus an mbedTLS buffer check; a write deadline

Why: decrypted data may sit inside mbedTLS where select on the socket cannot see it – without esp_tls_get_bytes_avail a read could wait despite data being ready. An overall write deadline stops the task from blocking when the server stops reading.

Cost: a more complex read loop.

D58. Magic packet 3× to two broadcast addresses

Why: UDP can be lost; some routers/APs filter 255.255.255.255, others the subnet broadcast. Repetition and two addresses improve reliability. Port 9 (discard) is the WoL convention.

Cost: a few extra packets.

D59. Separate client task and console, task notification

Why: WolClient::run blocks; the console runs in its own REPL task. xTaskNotifyGive wakes the client right after claim is entered, without polling.

Cost: a 10 KB stack for the client task (TLS + cJSON).

11.7 Deployment and tests

D60. Docker Compose with PostgreSQL, an unprivileged user, STOPSIGNAL SIGINT

Why: one command starts the database and server; the database healthcheck enforces start order. The server runs as the system user wol. It shuts down cleanly on KeyboardInterrupt, so Docker sends SIGINT instead of SIGTERM. Certificates are mounted read-only.

Cost: depends on Docker for this deployment path.

D61. Integration tests over real TLS and PostgreSQL

Why: trustme generates a CA and certificate per test, the server starts on port 0, each test gets its own database schema. Tests exercise the whole stack (TLS, framing, dispatcher, SQL) the way a client uses it. Database-free tests (transport) always run.

Cost: the full suite needs TEST_DATABASE_URL.

A detailed step-by-step guide is in README.md (Polish). The essentials:

  1. Certificate: openssl req -x509 ... with a CN/SAN matching the server address; copy server.crt to client/assets/server.pem and esp_client/main/certs/server.crt.
  2. Server: .env with TOKEN_PEPPER and DATABASE_URL (or POSTGRES_PASSWORD for Compose), optionally SMTP_*. docker compose up -d --build or python -m wol_server.
  3. App: expo.extra.serverHost/serverPort in app.json; npm ci, npm run android or npm run build:apk.
  4. Firmware: idf.py menuconfig → "Wake-on-LAN client" (WOL_WIFI_SSID, WOL_WIFI_PASSWORD, WOL_SERVER_HOST, WOL_SERVER_PORT, optionally WOL_CLAIM_TOKEN, WOL_SKIP_CN_CHECK for development only); idf.py build flash monitor.
The default sdkconfig.defaults enables flash encryption – the first boot writes a key into eFuse. The release profile (Secure Boot v2) is irreversible. Read the security section of PROTOCOL.md before the first flash.
